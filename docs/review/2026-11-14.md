## 1. Bugs

### Fixed (`fix/review-security-hardening`)
- **Returning guests weren't treated as guests (security).** Only *new* guests got the `guest` claim in their token.
  The site refreshes the token on every visit, and the refresh endpoint issued a normal token, so a returning guest
  passed every `IsSignedIn` check. That let a guest start linking Discord, and made `UpdateUserCommandHandler`'s
  spoofing check behave differently for new and returning guests. Now one `GenerateJwtToken` adds the claim from the
  user for every token. This also removes the separate **10-year** guest token: guests now get the same 15-minute
  token and renew through the refresh flow.
- **Internal API with no key configured.** If `InternalApiKey` was unset, a request with an empty
  `X-Internal-Api-Key` header matched it. Now nothing gets through without a configured key, and the comparison is
  constant-time.
- **Guests linking Discord got a 500** (an unhandled `UnauthorizedAccessException`). Now a 403 with a message.
- **Shared `Random` across requests.** Three handlers used one static `Random`, which isn't thread-safe; under
  concurrent requests it can start returning zeros (the same bot recipient, the same lobby code attempts). Now
  `Random.Shared`.

### Not fixed (need a decision or more than a guess)
- **`RedisGameCache.GetAllGamesAsync` breaks on a multi-node Redis.** It scans keys on
  `GetEndPoints().SingleOrDefault()`, which throws with more than one endpoint (replicas or a cluster), and `KEYS`
  scans don't scale. You mentioned scaling out, so I'd keep a Redis set of today's game IDs instead. It also turns a
  Redis failure into a **400** (`BadRequestException`); it should be a 500.
- **`GetIpAddress` trusts `X-Forwarded-For` as-is.** It's only stored with refresh tokens, so the impact is
  misleading audit data. Use ASP.NET's forwarded-headers middleware with your proxy's address.
- **Avatar upload errors go to `Console.WriteLine`** (`AvatarStorageService`, `UpdateUserCommandHandler`), so they
  never reach Application Insights. Use `ILogger`.

## 2. Architecture and code smells

**What's good:** clear project boundaries, thin controllers, MediatR commands and notifications used consistently,
feature folders, and integration tests against real SQL Server and Redis. The recent refactors (game processing,
pushes, pick rules, the lobby page) are covered by tests.

**Worth fixing:**
1. **.NET 8 support ended on November 10, 2026.** The app no longer gets security patches. Upgrade to **.NET 10**
   (the current LTS; the SDK is already installed here). This is the biggest item in the review. EF Core,
   ASP.NET Core and the Functions worker move together, so plan it as one PR.
2. **Migrations run at Web startup, and failures are swallowed.** `MigrateDatabase` logs the error and starts the app
   anyway, against a schema it doesn't match. With several replicas, they'd all try to migrate at once. Better:
   apply migrations as a deploy step (`dotnet ef migrations bundle`), or at least fail startup when it fails.
3. **Mixed routing.** `UseMvc` with `EnableEndpointRouting = false`, plus `UseEndpoints`, plus a SPA fallback. This
   is the pre-.NET-Core-3 style. `MapControllers` + `MapFallbackToController` replace all of it, and the .NET 10
   upgrade will push you there anyway.
4. **Server-side validation lived only in the forms** for chat length, picks per team, game lists and bot count.
   Fixed on the hardening branch (`LobbyRules`, `SendLobbyMessageCommandHandler`). Worth a pass over the remaining
   commands with the same eye.
5. **`DraftPuck.Shared` holds both entities and DTOs.** It works, but the line between the database model and the
   API contract is blurry (entities are sometimes returned or patched directly). Not urgent.

## 3. Ideas

- **Admin page for event logos** (list, add, remove), so you don't need SQL.
- **End-of-night recap**: who drank the most, best pick, biggest steal, as a shareable card.
- **Smaller game pushes**: send only what changed, or only to lobbies that include the game, as traffic grows.
- **Rate limiting** on login, guest creation and chat (`POST /api/users` creates a database row for anyone, with no
  limit). ASP.NET's built-in limiter is per instance, which is fine as a first line of defense **(guess: acceptable
  for you, given your concerns about in-memory state)**; a Redis-backed limiter if it must be shared.
- **Health checks** (`/health` covering SQL, Redis, storage) for the container platform and uptime monitoring.
- **OpenAPI/Swagger in development**: `AddEndpointsApiExplorer` is already registered but nothing serves it.
- **Security headers**: a Content-Security-Policy, `X-Content-Type-Options` and `frame-ancestors`. The JWT lives in
  `localStorage`, so a CSP is the main protection if an HTML-escaping bug ever slips through.

## 4. Would a contributor have an easy time?

**Mostly yes.** Feature folders make code easy to find, `CONTRIBUTING.md` explains branches and both test suites,
and CI runs both on every PR.

**Gaps:**
- **`README.md` linked to a `docs/architecture.md` that didn't exist.** Added on `docs/architecture-guide`: projects,
  how requests, games and real-time updates flow, the key domain rules, and where new code goes.
- **Setup assumes Visual Studio** (the docker-compose launch profile). There's no command-line path for VS Code or
  Rider users.
- **No `dotnet-ef` in a tool manifest**, so adding a migration needs a global tool. `dotnet new tool-manifest` plus
  `dotnet tool install dotnet-ef` makes `dotnet ef` work for everyone at a pinned version.
- **No PR or issue templates.** A short PR checklist (tests, migration, screenshots) would help.
- **Mixed line endings in the working tree.** `.gitattributes` normalizes commits, so it's cosmetic, but every commit
  warns. A one-time `git add --renormalize .` cleans it up.

## 5. Security and packages

and **MessagePack**, plus moderate ones in **OpenTelemetry**. All fixed with patch or minor bumps within the current
